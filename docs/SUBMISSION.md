# XScan — материалы для сдачи

Команда Zhalpakov Team · Datathon 26 (Nazarbayev University × ForteBank)

XScan проверяет видеозапись кассы (`.mov`, ракурс сверху, без звука) и выдаёт вердикт на всё видео, список возможных нарушений с таймкодом, 1–3 кадрами-доказательствами, описанием и ссылкой на норматив РК. Результат — подсказка проверяющему, а не юридическое заключение.

## 1. Доступ

| | |
|---|---|
| Веб-интерфейс | https://xscan-azac.onrender.com/design/ |
| Базовый адрес API | https://xscan-azac.onrender.com |
| Ключ API | передаётся в форме сдачи (заголовок `X-API-Key`) |

Сервис работает на бесплатном тарифе хостинга: после 15 минут без запросов он засыпает, и первый запрос будит его примерно за минуту.

### Как вызвать API

```bash
curl -H "X-API-Key: <ключ>" -F "file=@video.mov" https://xscan-azac.onrender.com/api/v1/analyze
# -> {"job_id": "8e3aef8682ad", "status": "processing"}

curl -H "X-API-Key: <ключ>" https://xscan-azac.onrender.com/api/v1/jobs/8e3aef8682ad
# -> {"job_id": "...", "status": "done", "verdict": "violation", "violations": [
#      {"type": "...", "timecode_sec": 12.5, "description": "...",
#       "evidence_frames": [{"timestamp_sec": 12.5, "image_base64": "<JPEG>"}]}]}
```

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/v1/analyze` | multipart, поле `file` (`.mov`) → `job_id`, статус `processing` |
| GET | `/api/v1/jobs/{job_id}` | `processing` / `done` / `failed`, вердикт `violation` / `no_violation`, нарушения |
| GET | `/health` | состояние сервиса |

Без ключа API отвечает `401`. Видео до 500 МБ; на одно видео отводится не больше 240 с, чтобы уложиться в лимит 5 минут.

## 2. Инструкция по запуску

```bash
git clone https://github.com/zhaparzhiger/xscan && cd xscan
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt        # Linux/Mac: .venv/bin/pip
```

Создать `.env` в корне:

| Переменная | Что это |
|---|---|
| `API_KEY` | ключ для заголовка `X-API-Key` |
| `ANALYZER` | `vlm` — основной режим (мультимодальная модель), `local` — запасной офлайн-режим |
| `VLM_MODEL`, `VLM_FALLBACK_MODELS` | идентификатор модели и запасные модели через запятую |
| `GOOGLE_APPLICATION_CREDENTIALS` | путь к JSON сервисного аккаунта для доступа к модели (или `VLM_API_KEY`) |
| `UI_USERS` | пользователи веб-интерфейса, строку печатает `python scripts/make_user.py <логин>` |
| `SESSION_SECRET` | секрет подписи сессий |
| `UI_DEMO_LOGIN`, `UI_DEMO_PASSWORD` | тестовая учётка, показывается на экране входа |
| `WORKERS` | сколько видео обрабатывать параллельно (по умолчанию 1, на сервере 3) |

Запуск:

```bash
.venv/Scripts/python -m uvicorn app.main:app --port 8010
# интерфейс: http://localhost:8010/design/
```

Развёртывание на Render описано в `render.yaml` (Blueprint): секреты вставляются в панели Render, в репозитории их нет.

Замер на размеченных видео: `python ml/eval_vlm.py` (папка с видео — в переменной `XSCAN_VIDEOS`). Результат появляется на странице «Замер» в интерфейсе.

## 3. Архитектура, подход и модели

```
 Веб-интерфейс (design/)          Жюри / внешние системы (X-API-Key)
         │ /ui/*                           │ /api/v1/*
         └──────────────┬──────────────────┘
                        ▼
        FastAPI (app/main.py) → очередь задач (app/jobs.py, WORKERS потоков, статусы на диске)
                        │
                        ▼
        app/pipeline/analyze.py
          1. video.py      — длительность, чтение кадров (OpenCV)
          2. vlm.py        — видео ужимается на сервере (512 px, ~5 кадров/с, без звука)
                             и анализируется мультимодальной моделью по API;
                             ответ — строгий JSON по схеме: вердикт, типы, таймкоды, что видно
          3. нормализация  — таймкоды в пределах видео, дубли одного типа ближе 3 с склеиваются
          4. rules/registry — описание и норматив подставляются из проверенной базы
                             (app/rules/violations.yaml); модель ссылки на законы не пишет
          5. video.py      — 1–3 кадра-доказательства из исходного видео (JPEG, base64)
                        │
                        ▼
        JSON по разделу 10 ТЗ  +  Bot API (/bot-api/*) для внешних агентов-процессов
```

**Подход.** Модели дают описание сцены и правила, что считается нормой и что нарушением (например: клиент, который зашёл на обслуживание, — норма; пересчёт денег клиента после его ухода — нарушение). Таймкод — момент, когда нарушение начинается. Вердикт на всё видео: `violation`, если найдено хотя бы одно нарушение.

**Агенты.** В интерфейсе каждый тип нарушения представлен агентом («Посторонний у кассы», «Деньги клиента», «Сейф и дверь» и т. д.); агент загорается, когда найдено нарушение его типа. Служебные агенты: «Юрист» подбирает норматив только из проверенной базы, «Агрегатор» собирает вердикт. Через Bot API к задаче могут подключаться внешние агенты-процессы (пример — `scripts/agent_motion.py`, детектор движения).

**Исследования, которые привели к этому решению** (кросс-валидация по видео, подробности в `HANDOFF.md`):

| Подход | Результат |
|---|---|
| CLIP ViT-B/32 + логистическая регрессия | recall 0.64 при 80% ложных тревог |
| SigLIP 2 (кадр + тайлы), позы KeypointRCNN | AUC по видео 0.35–0.48 |
| Qwen3-VL-4B локально, вопросы да/нет по кадрам | AUC по видео 0.47 |
| Рамки объектов Qwen3-VL + состояния (экран, сейф, стол) | лучшие признаки AUC 0.68–0.73, модели — на уровне случайного |

Вывод: на 21 нарушении в похожих друг на друга роликах обучать свой классификатор бессмысленно, а нормальные и нарушающие ролики отличаются деталями. Поэтому основной режим — мультимодальная модель с описанием правил, а офлайн-пайплайн (`ANALYZER=local`, CLIP + детектор) оставлен запасным.

## 4. Нормативные источники и принцип сопоставления

Используются только акты РК с adilet.zan.kz. Пункты записаны после чтения текста; где связь с видимым на видео косвенная, это сказано прямо. Если для вывода нужны невидимые на видео данные (документы, проводки, сверки), нарушение не утверждается.

1. **Постановление Правления НБРК от 24.02.2020 № 14** — Правила организации охраны и устройства помещений банков второго уровня… (рег. МЮ РК № 20075). https://adilet.zan.kz/rus/docs/V2000020075
2. **Постановление Правления НБРК от 29.11.2019 № 231** — Правила осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей… (рег. МЮ РК № 19680). https://adilet.zan.kz/rus/docs/V1900019680

**Принцип.** Тип нарушения → что видно на видео → документ → пункт. Связки хранятся в `app/rules/violations.yaml`; пункт выводится только для документов с отметкой `verified: true`. Подробный разбор пунктов — `docs/norms.md`.

## 5. Распознаваемые типы нарушений

| Тип (`type_id`) | Что видно на видео | Норматив |
|---|---|---|
| Посторонний в кассовом помещении (`unauthorized_person`) | человек, не являющийся кассиром, заходит за стол кассира, к сейфу или ценностям, остаётся в кассе без кассира | № 14, пп. 8 и 16 (подп. 1); № 231, п. 75 — косвенно |
| Кассир оставил ценности без присмотра (`cashier_left_workplace`) | кассир уходит, а деньги, ценности или разблокированный ноутбук остаются | № 231, п. 22, п. 20 ч. 2; п. 2 подп. 17 — косвенно |
| Сейф оставлен открытым (`safe_left_open`) | дверца сейфа или шкафа с ценностями открыта, рядом никого | № 231, п. 20 ч. 2, п. 80 |
| Личные вещи / еда на рабочем месте (`personal_items`) | телефон, еда, напитки, личные вещи на рабочем месте кассира | № 231, п. 12 |
| Нарушение порядка работы с наличными клиента (`cash_handling`) | деньги клиента пересчитывают или убирают после его ухода, оставляют открыто | № 231, без точного пункта |
| Нарушение порядка передачи ценностей — инкассация (`improper_handover`) | сумка или мешок с ценностями передаётся не по порядку | № 14, п. 21; № 231, пп. 24, 105–107 — документы по видео не проверяются |
| Дверь кассы открыта при работе с ценностями (`door_open`) | дверь кабинета распахнута, пока кассир работает с наличными | № 14, пп. 8 и 16 (подп. 1) — косвенно |
| Признаки возможного нарушения (`generic`) | нетипичное действие, не подходящее под известные типы (для новых типов в тесте) | № 231, без пункта |

## 6. Ограничения и известные ошибки

- **Замер на 40 размеченных видео организаторов** (дубликаты X-4/X-47 и X-5/X-48 склеены): найдено 14 нарушений из 21, ложная тревога на 1 нормальном видео из 19, вердикт верный в 80% видео; таймкод попадает в ±3 с в 7 случаях из 14; в среднем 22 с на видео, максимум 89 с. Правила для модели подбирались по этим же видео, поэтому на новых видео результат, скорее всего, будет немного хуже.
- **Пропуски.** Чаще всего пропускаются нарушения, которые отличаются от нормы мелкой деталью (X-1, X-2: работа с деньгами при клиенте; X-13: открытый сейф; X-32, X-33: дверь). Режим можно сделать чувствительнее ценой большего числа ложных тревог.
- **Таймкод.** Модель иногда ставит таймкод на момент начала сцены (вход человека), а не на сам момент нарушения; расхождение до 5–10 с.
- **Типы** проверить на данных нельзя: в разметке организаторов тип нарушения не указан.
- **Зависимость от API модели.** Для анализа нужен доступ к модели по сети; при перегрузке сервис пробует запасные модели и укладывается в бюджет 240 с, иначе задача завершается с ошибкой, а не «висит».
- **Хостинг.** Бесплатный тариф засыпает после 15 минут без запросов; диск не постоянный — при перезапуске сервиса незавершённые задачи и история пропадают.
- **Не анализируются** звук и лица (требование ТЗ). Нарушения, которые требуют документов (проводки, препроводительные), не утверждаются.
- **Агенты и «Обучение» в интерфейсе.** Деление на агентов отражает типы нарушений; страница «Обучение» — макет интерфейса будущей функции дообучения, реальное обучение по загруженному ZIP пока не подключено.
